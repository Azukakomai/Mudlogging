\chapter{RESEARCH METHODOLOGY}

\section{Research Design and Software Engineering Life Cycle}

This research develops a dedicated web-based decision support system to automate the processing, multi-ratio comparative analysis, and visualization of Gas While Drilling (GWD) data, as well as deterministic hydrocarbon fluid classification. Because the platform is delivered as an interactive, production-ready scientific application, the research methodology strictly adheres to established Software Engineering (SE) best practices. The development follows a structured five-phase Software Development Life Cycle (SDLC) tailored for scientific computing and formation evaluation:

\begin{enumerate}
    \item \textbf{Requirements Analysis and Specification:} Systematically eliciting and defining both functional requirements (e.g., multi-format log ingestion, automated 16-parameter petrophysical indicator calculation, fluid zone classification, multi-track vertical visualization) and non-functional requirements (e.g., sub-5-second processing latency, mathematical auditability, user-friendly interface, zero commercial licensing barriers). End-user needs and domain pain points are gathered via structured questionnaires distributed to practicing geoscientists, wellsite engineers, and academic researchers.
    
    \item \textbf{System and Architectural Design:} Formalizing the system blueprint through a decoupled three-tier modular software architecture consisting of a Data Ingestion Layer, a Deterministic Logic Engine Layer, and a Reactive Presentation Layer. This phase encompasses algorithmic flow design, schema definitions, mathematical decision-matrix mapping, and modal-based UI/UX wireframing in Dash.
    
    \item \textbf{Software Implementation:} Translating architectural designs into modular, clean, and maintainable Python code (\texttt{parser.py}, \texttt{engine.py}, \texttt{evaluator.py}, and \texttt{app.py}). Because the calculation core operates strictly on closed-form petrophysical laws and explicit boundary thresholds, the system undergoes a data-free deterministic build phase requiring no empirical training or stochastic machine learning fitting.
    
    \item \textbf{System Testing and Evaluation:} Executing multi-level verification and empirical evaluation. This includes algorithmic unit verification against exact mathematical benchmarks, end-to-end computational throughput profiling ($\Delta t_{\text{total}} \le 5.0\text{ s}$), and user-driven field evaluation where domain experts process real-world well logs and record standardized usability scores ($\overline{S} > 68.0$).
    
    \item \textbf{Software Release and Deployment:} Packaging the application with standardized environment dependencies (\texttt{requirements.txt}), enabling containerized or local web execution, and publishing the software to an open-source public repository for transparent community verification and democratized academic access.
\end{enumerate}

\section{Requirements Analysis and Specification}

Establishing rigorous software engineering requirements ensures that the developed application directly solves operational bottlenecks in formation evaluation while maintaining strict technical feasibility.

\subsection{Functional Requirements (FR)}
The functional specifications define the operational capabilities that the system must deliver:
\begin{itemize}
    \item \textbf{FR-01 (Multi-Format Ingestion):} The system must ingest raw mud logging files in multiple standard tabular and text formats (\texttt{.txt}, \texttt{.csv}, and \texttt{.xlsx}), automatically stripping proprietary metadata headers.
    \item \textbf{FR-02 (Continuous Data Normalization):} The system must validate, clean, and normalize chromatographic gas curves ($C_1$ through $C_5$) against Measured Depth ($MD$), handling missing or zero values without pipeline termination.
    \item \textbf{FR-03 (Multi-Ratio Deterministic Computation):} The calculation engine must automatically compute 16 derived petrophysical indicators from input gas curves in real time.
    \item \textbf{FR-04 (Automated Fluid Zone Classification):} The system must apply deterministic decision-tree logic to classify each depth interval into categorical fluid regimes: Gas Zone, Oil Zone, or Water/Non-Productive Zone.
    \item \textbf{FR-05 (Interactive Multi-Track Visualization):} The frontend must render continuous, depth-synchronized vertical area charts for all computed indicators and fluid zones, allowing dynamic zooming, panning, and tooltips.
    \item \textbf{FR-06 (Export and Reporting):} The system must allow users to export calculated indicator curves and classification summaries for external technical reporting.
\end{itemize}

\subsection{Non-Functional Requirements (NFR)}
Non-functional specifications ensure software quality, robustness, and usability:
\begin{itemize}
    \item \textbf{NFR-01 (Computational Latency):} The end-to-end processing pipeline (ingestion, calculation, and rendering) must complete in under 5.0 seconds for log trajectories spanning thousands of meters.
    \item \textbf{NFR-02 (Auditability and Determinism):} All calculations must operate on explicit, transparent formulas with zero "black-box" opacity, ensuring 100\% mathematical reproducibility required by industry reporting standards \citep{ref3}.
    \item \textbf{NFR-03 (Usability and Learnability):} The interface must provide an intuitive workflow accessible without extensive training, achieving a mean System Usability score of $\overline{S} > 68.0$.
    \item \textbf{NFR-04 (Accessibility and Openness):} The application must operate using open-source Python technologies, eliminating multi-thousand-dollar licensing barriers associated with commercial petrophysical suites \citep{wood2020}.
\end{itemize}

\subsection{Requirements Elicitation}
Requirements were elicited through a domain-specific survey distributed to practicing wellsite engineers, mud logging specialists, and petroleum geologists via Google Forms. The survey gathered feedback regarding routine GWD workflows, commonly utilized gas ratios, limitations of existing commercial software suites, and preferred visualization layouts.

\section{System Architecture and Design}

To ensure high maintainability, separation of concerns, and computational efficiency, the platform is designed using a decoupled three-tier modular software architecture.

\subsection{Three-Tier Architectural Overview}
The software architecture separates data processing into three distinct layers:
\begin{enumerate}
    \item \textbf{Data Parsing \& Ingestion Layer (\texttt{parser.py}):} Responsible for file uploading, format detection, header isolation, data sanitization, and structured matrix generation.
    \item \textbf{Deterministic Logic Engine Layer (\texttt{engine.py} \& \texttt{evaluator.py}):} Implements the closed-form petrophysical mathematical formulas, vectorizes curve computations, and executes the categorical zone decision matrix.
    \item \textbf{Presentation \& Dashboard Layer (\texttt{app.py}):} Constructed with Dash and Plotly, providing a reactive web user interface with responsive controls and depth-registered multi-track charts.
\end{enumerate}

\subsection{Data Parsing \& Ingestion Layer Design}

The ingestion pipeline isolates valid numeric data matrices from raw field logs through a systematic two-stage process:

\begin{enumerate}
    \item \textbf{Metadata and Header Isolation:} Raw mud logs frequently begin with irregular operator metadata and unstructured comments. The parser scans the incoming stream line-by-line using keyword triggers (such as \texttt{\char`~A} or \texttt{Depth}) to bypass non-tabular headers and locate the column index.
    \item \textbf{Data Normalization and Type Casting:} Delimited lines (supporting tabs, commas, and whitespace) are stripped of non-numeric artifacts and converted into structured float matrices indexed continuously by measured depth ($MD$). Missing, negative, or null entries are handled systematically to prevent pipeline interrupts.
\end{enumerate}

\subsection{Petrophysical Indicators \& System Decision Logic Design}

A primary objective of this application is to provide geoscientists with a comprehensive comparative suite within a single dashboard. Different eras and regional standards in petroleum geology rely on varying interpretation methods. To allow users to cross-compare results from legacy frameworks with modern expanded indicators, the system integrates a wide array of both classical and updated formulas. The data pipeline takes parsed hydrocarbon gas curves ($C_1$ through $C_5$) and automatically computes 16 derived parameters alongside automated fluid-zone predictions.

\subsubsection{Pixler Hydrocarbon Ratios}
The system evaluates light hydrocarbon fractions using the classic ratio framework established by \citet{ref13} to distinguish dry gas intervals from productive oil-bearing formations:

\begin{equation}
    \text{Ratio}_1 = \frac{C_1}{C_2}
\end{equation}

\begin{equation}
    \text{Ratio}_2 = \frac{C_1}{C_3}
\end{equation}

\begin{equation}
    \text{Ratio}_3 = \frac{C_2}{C_3}
\end{equation}

A very high $C_1/C_2$ ratio indicates dry methane gas, while lower values reflect increasing concentrations of heavier, liquid-associated hydrocarbons \citep{ref13}.

\subsubsection{Expanded Light-to-Heavy Butane Multipliers}
To utilize modern chromatographic logs that split butane into individual isomers, the engine tracks methane against specific butane paths:

\begin{equation}
    \text{Ratio}_4 = \frac{C_1}{iC_4}
\end{equation}

\begin{equation}
    \text{Ratio}_5 = \frac{C_1}{nC_4}
\end{equation}

Tracking isobutane ($iC_4$) and normal butane ($nC_4$) separately provides heightened sensitivity to heavy, liquid-rich reservoir boundaries.

\subsubsection{Total Gas Volume ($TG$) and Dryness Ratio}
When Total Gas ($TG$) is not pre-recorded in the uploaded log, the baseline is computed by summing all recorded hydrocarbon fractions \citep{ref14}:

\begin{equation}
    TG = C_1 + C_2 + C_3 + iC_4 + nC_4 + iC_5 + nC_5
\end{equation}

The Dryness Ratio is then computed to isolate the methane purity of the gas mixture:

\begin{equation}
    \text{Dryness} = \frac{C_1}{TG}
\end{equation}

\subsubsection{Carbon-Weighted Density Index ($I_{\text{carbon}}$)}
To quantify carbon density across the gas stream, the system implements a weighted index where each alkane fraction is scaled by its carbon atom count:

\begin{equation}
    I_{\text{carbon}} = \frac{TG}{C_1 + 2C_2 + 3C_3 + 4iC_4 + 4nC_4 + 5iC_5 + 5nC_5}
\end{equation}

Because liquid hydrocarbons contain longer carbon chains, a lower $I_{\text{carbon}}$ value indicates a shift toward heavier petroleum fluids.

\subsubsection{Expanded Haworth Gas Ratios}
The system implements both standard and expanded forms of the Show Evaluation framework established by \citet{haworth1985} and \citet{ref12}, incorporating modern $C_4$ and $C_5$ fractions:

\begin{equation}
    W_h = \left( \frac{C_2 + C_3 + iC_4 + nC_4 + iC_5 + nC_5}{TG} \right) \times 100
\end{equation}

\begin{equation}
    B_h = \frac{C_1 + C_2}{C_3 + iC_4 + nC_4 + iC_5 + nC_5}
\end{equation}

\begin{equation}
    C_h = \frac{iC_4 + nC_4 + iC_5 + nC_5}{C_3}
\end{equation}

These three expanded parameters form the core fluid-typing decision framework: Wetness ($W_h$) evaluates fluid richness, Balance ($B_h$) delineates gas-liquid contacts, and Character ($C_h$) confirms fluid typing \citep{haworth1985, ref12}.

\subsubsection{Composite Fluid and Gas-Oil Ratio (GOR) Indicators}
To automate zone classification, the engine utilizes composite indicators that isolate heavy fractions \citep{whittaker1991, spe2020}:

\begin{equation}
    GOW = (C_3 + iC_4 + nC_4 + iC_5 + nC_5) \times TG
\end{equation}

\begin{equation}
    GOW_{\text{noTG}} = \frac{GOW}{TG^2}
\end{equation}

The $GOW_{\text{noTG}}$ indicator decouples heavy gas composition from total gas fluctuations caused by drilling mud weight changes or penetration rate variations. Additionally, the system calculates the combined Wetness-Balance Score ($WBS$):

\begin{equation}
    WBS = \frac{\log(B_h) - 0.903}{2.097} - \frac{\log(W_h)}{2}
\end{equation}

A conditional Gas-Oil Ratio ($GOR$) screening index is applied based on established engineering thresholds \citep{ref14, spe2020}:

\begin{equation}
    GOR = \begin{cases} 0 & \text{if } 0.8 < TG < 1.2 \text{ and } C_1 > 2000 \text{ ppm} \\ 1 & \text{otherwise} \end{cases}
\end{equation}

These multi-ratio outputs feed into a deterministic rule matrix \citep{ref1} that classifies every depth increment into categorical zones: "Gas Zone," "Oil Zone," or "Water/Non-Productive Zone."

\subsection{User Interface \& Visualization Architecture Design}

The frontend is constructed using the \textit{Dash Python Framework} with \textit{dash-bootstrap-components} (\texttt{dbc}) to replace legacy, complex desktop interfaces with a modern, responsive web dashboard:

\begin{itemize}
    \item \textbf{Reactive Pipeline (\texttt{app.callback}):} Callbacks detect file uploads or threshold adjustments, executing the deterministic calculation engine in memory and updating visual graphs instantaneously without full page reloads.
    \item \textbf{Modal File Ingestion (\texttt{dcc.Upload} \& \texttt{dbc.Modal}):} File parsing controls are containerized inside modal dialogs to maintain a clean workspace.
    \item \textbf{Multi-Track Plotly Visualizations:} Processed indicators and zone classification flags are mapped to continuous vertical area tracks locked to measured depth ($MD$), replicating standardized wellsite mud logging templates.
\end{itemize}

\section{Software Implementation}

The implementation phase translates the architectural blueprints into modular, maintainable Python source modules adhering to clean code standards and scientific computing best practices.

\subsection{Implementation Principles and Modularity}
The codebase is structured into cohesive modules with distinct responsibilities:
\begin{itemize}
    \item \texttt{parser.py}: Implements automated ASCII and spreadsheet parsing, column regex matching, and missing value interpolation.
    \item \texttt{engine.py}: Encapsulates the 16 petrophysical ratio formulas and categorical decision logic, utilizing vectorized NumPy and Pandas operations for maximum throughput.
    \item \texttt{evaluator.py}: Houses ground-truth validation routines, confusion matrix generators, and statistical metric computations.
    \item \texttt{app.py}: Integrates the backend calculation pipelines into Dash reactive callbacks and constructs the interactive Bootstrap layout.
\end{itemize}

\subsection{Data-Free Deterministic Build Phase}
Because the system is purely deterministic---operating strictly on closed-form petrophysical formulas and explicit boundary thresholds---the system development requires no empirical training data or stochastic machine learning fitting during construction. The algorithms are coded directly from physical equations and validated against exact analytical test matrices.

\subsection{Reactive Dashboard Execution}
The application utilizes Dash reactive state management. When a user uploads a new dataset, the data is decoded in memory, processed through vectorized NumPy ratio functions, and rendered across synchronized Plotly subplots, ensuring that no temporary data is leaked or permanently stored on unauthenticated servers.

\section{System Testing and Performance Evaluation}

Because the core processing engine is strictly deterministic and operates on established mathematical laws rather than stochastic machine learning models, validation follows a rigorous testing strategy covering three dimensions: algorithmic verification, computational latency, and user usability.

\subsection{Algorithmic Verification}
Algorithmic verification validates that every mathematical equation in the code matches its closed-form theoretical counterpart. Unit tests execute against synthetic benchmark tensors with known inputs and expected outputs, guaranteeing zero floating-point drift or calculation errors across all 16 ratio indicators.

\subsection{End-to-End Computational Throughput ($< 5$ Seconds)}
In active drilling operations, operational decision windows are narrow. System efficiency is evaluated by measuring the total latency ($\Delta t_{\text{total}}$) spanning the entire automated pipeline:
\begin{equation}
    \Delta t_{\text{total}} = t_{\text{ingest}} + t_{\text{compute}} + t_{\text{render}}
\end{equation}
The benchmark target requires $\Delta t_{\text{total}} \le 5.0\text{ seconds}$ when processing dense mud logging datasets spanning thousands of meters of depth ($> 3000\text{ m}$ trajectories).

\subsection{User Usability Evaluation}

To validate the practical utility, interface clarity, and user satisfaction of the deployed platform, system usability is evaluated through structured feedback sessions with practicing geoscientists, wellsite engineers, and peer researchers. After testing the application with real-world well logging datasets, each evaluator completes a structured evaluation form via Google Forms. The questionnaire consists of 10 targeted usability and functionality questions, with each item rated on a standard linear scale from 1 (poor) to 10 (excellent). An evaluator's total usability score ($S_{\text{user}}$) is calculated by summing their ratings across all 10 items, yielding a possible total score ranging from 10 to 100 points:

\begin{equation}
    S_{\text{user}} = \sum_{i=1}^{10} q_i
\end{equation}

where $q_i \in [1, 10]$ represents the individual score assigned to question $i$. The overall system usability performance is measured by computing the average total score ($\overline{S}$) across all $N$ evaluators:

\begin{equation}
    \overline{S} = \frac{1}{N} \sum_{k=1}^{N} S_{\text{user}, k}
\end{equation}

To confirm that the software delivers a highly intuitive and acceptable user experience, the benchmark target for this research is established at a mean total usability score of $\overline{S} > 68.0$ out of 100.

\section{Software Release and Deployment}

The final phase of the software engineering life cycle encompasses packaging, deployment, and distribution to ensure long-term accessibility and reproducibility.

\subsection{Packaging and Dependency Management}
The software dependencies are explicitly specified in a standardized \texttt{requirements.txt} manifest, fixing versions for core libraries (\texttt{dash}, \texttt{dash-bootstrap-components}, \texttt{plotly}, \texttt{pandas}, \texttt{numpy}, and \texttt{openpyxl}). This guarantees consistent environment reproduction across Windows, Linux, and macOS platforms without dependency conflicts.

\subsection{Open-Source Distribution and Accessibility}
To fulfill the research objective of democratizing petrophysical tools and eliminating prohibitive commercial licensing costs \citep{wood2020}, the application is released under an open-source license hosted on a public version-controlled repository (GitHub). The repository contains comprehensive documentation, installation instructions, sample dataset templates, and full source code to enable peer review, academic replication, and continuous community enhancement.
